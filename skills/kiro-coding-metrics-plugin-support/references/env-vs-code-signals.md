# 环境问题 vs 代码问题 判断指南

把症状分类的目的：决定**让用户改配置**还是**让开发者改代码**。判断错代价很高（用户绕弯/同问题反复出现）。

---

## 信号矩阵

### 强信号：环境问题

| 信号 | 含义 | 例子 |
|------|------|------|
| 仅特定 OS 复现 | 多半是平台相关配置 | 仅 Windows 失败 → 路径分隔符 / GBK 编码 / curl 不存在 |
| 改路径/重装/换网络后好了 | 用户操作改变了环境 | 把 repo 移到不含中文/空格的路径 → 工作 |
| 同事的相同 workspace 不出问题 | 用户机器特殊 | 用户装了 AppLocker / 改了 PATH |
| 错误信息含 OS 系统层级提示 | 系统调用层失败 | `EACCES`, `ENOENT`, `cannot execute binary file` |
| 现象与时间相关 | 外部因素 | 公司断网时刻、系统更新后 |
| 同一插件版本不同人不同表现 | 环境差异 | A 用户数据正常，B 用户全 0 |

### 强信号：代码 bug

| 信号 | 含义 | 例子 |
|------|------|------|
| 100% 必现 | 输入→输出确定性错 | 所有 amend commit 数据都为 0 |
| 跨平台都能复现 | 与 OS 无关 | macOS/Windows 都漏空行归属 |
| 代码逻辑明显错误 | 看了源码就知道 | `if (orig === undefined)` 把删除文件场景跳过了 |
| 边界条件未覆盖 | 设计漏洞 | 文件路径含 `..` 时拼接出错 |
| Workaround 是改用户配置但同问题反复 | 没修根因 | 让用户避免使用 amend，但 amend 是合理操作 |

### 弱信号 / 模糊信号（需要进一步分析）

| 现象 | 可能性 | 怎么进一步判断 |
|------|--------|-------------|
| 部分用户复现，部分不复现 | 环境 70% / 代码 30% | 找到不复现用户的差异变量 |
| 偶发出现 | 时序/并发 50% / 配置 50% | 看是否能找到触发条件 |
| 用户报告"今天不工作" | 用户改了什么 50% / 系统更新 30% / 代码升级 20% | 问"昨天到今天有什么变化" |
| 重启后好了 | 状态/缓存 80% / 代码 20% | 看是否有持久化错误状态 |

## 真实案例（来自项目实践）

### 案例 1：macOS 上 post-commit 不能上报 → **环境 + 代码混合**

**现象**：所有 macOS 用户都报上报失败。

**初判**：100% 必现 + 跨用户 → 像代码 bug。

**深挖发现**：
- 插件 `bin/` 目录下打包了 `curl.exe`（Windows binary）— 这是**打包配置**问题
- hook 的判断逻辑 `if [ -f "$CURL_CMD" ]` 在 macOS 上发现 `curl.exe` 存在就用它 — 这是**代码逻辑**问题

**分类**：表面是代码 bug（hook 逻辑没考虑文件名误导），但根因是打包/分发的环境假设错误（不该把 Windows binary 同时分发到 macOS）。

**正确处理**：代码修复 — 用 `uname -s` 显式检测平台。

**教训**：当现象跨用户必现时，几乎一定是代码 bug；环境差异只决定 bug 是否暴露。

### 案例 2：Windows 上中文 commit message 上报失败 → **代码 bug，环境暴露**

**现象**：仅 Windows 中文 commit message 失败。

**初判**：仅特定 OS + 特定字符 → 像环境问题。

**深挖发现**：
- 在所有 shell 上，`COMMIT_MSG=$(git log ...)` 都会让字节流经过 shell 编码处理
- Windows GBK 默认编码下，git 输出的 UTF-8 字节会被错误转码
- 修复必须在代码层（让 commit_msg 不进入 shell 变量），不能让用户改环境（用户不应改 GBK→UTF-8）

**分类**：代码 bug（对 shell 编码的不安全假设），Windows 中文环境碰巧暴露。

**正确处理**：代码修复 — commit_msg 写文件 + curl 用 `-d @file`，全程绕开 shell 变量。

**教训**：现象在特定环境出现 ≠ 环境问题。要看"修复要在哪一层做"。

### 案例 3：Windows sh.exe 探测失败 → **环境问题**

**现象**：A 用户 Windows sh hook 工作，B 用户 Windows 上日志显示 "sh.exe not available"。

**深挖发现**：
- B 用户从 .lnk 快捷方式启动 Kiro，子进程 PATH 不继承用户完整 PATH
- A 用户从开始菜单启动 Kiro，PATH 完整
- B 的环境配置（启动方式）导致 spawnSync("sh") 找不到

**分类**：本质环境问题（启动方式、PATH 配置），但代码可以变得更鲁棒。

**正确处理**：代码增强 — 用 `git --exec-path` 推断 sh.exe 路径，不仅依赖 PATH。

**教训**：环境问题如果会反复出现，应该让代码做"防御性增强"。让代码处理常见环境差异，比让所有用户改启动方式现实。

### 案例 4：跨同级目录 git repo 不识别 → **代码 bug**

**现象**：workspace 是 `git-ai`，同级 `test` 是另一个 git 项目。AI 在 `test` 下编辑，插件不识别。

**深挖发现**：
- `findRepoForFile` 用 `startsWith` 前缀匹配
- Windows 上 `path.resolve` 返回的盘符是大写 `D:`，但 `vscode.git` API 给的 repo path 是小写 `d:`
- 100% 必现，与具体用户无关

**分类**：代码 bug — 没考虑 Windows 文件系统大小写不敏感。

**正确处理**：代码修复 — Windows 平台做大小写不敏感前缀匹配。

**教训**：能 100% 复现的基本都是代码。

### 案例 5：amend commit 数据全计入人工 → **代码 bug**

**现象**：所有 amend commit 数据都错。

**深挖发现**：
- hook 用 `ORIG_HEAD` 取被 amend 的原始 commit SHA
- `git commit --amend` 不更新 `ORIG_HEAD`，所以拿到的 SHA 是之前 rebase/merge 留下的不相关值
- 跨平台跨用户都必现

**分类**：代码 bug — 对 git 行为的假设错误。

**正确处理**：代码修复 — 用 `HEAD@{1}` 替代 `ORIG_HEAD`。

**教训**：当依赖第三方工具的行为时，要验证假设。

## 判断流程图

```
症状报告
   ↓
是否 100% 必现？
   ↓
   ├─ 是 → 跨平台/跨用户都复现？
   │       ├─ 是 → 代码 bug
   │       └─ 否 → 平台特定的代码 bug，但环境暴露（修代码）
   │
   └─ 否 → 是否能找到唯一变量？
           ├─ 找到（OS/路径/权限）→ 环境问题（让用户改）
           ├─ 找到（特定输入数据）→ 代码 bug（边界条件）
           └─ 找不到 → 时序/并发，深挖（看日志时间戳）
```

## 给开发者的修复建议（如果是代码）

要包含：

1. **症状的可复现 minimal test case**（用户提供的 SHA / 文件 / 操作步骤）
2. **根因定位到的具体函数**（GitHub 路径 + 行号范围）
3. **建议的修改方向**（不一定是最终方案，但要给思路）
4. **测试要点**（修复后如何验证）

例：
```
症状：amend commit 数据全部计入人工
复现：用户 commit SHA 16d8df9（amend from 60064e1）
根因：kiro-pugin/src/gitUtils.ts buildHookSectionUnix 中
     OLD_SHA=$(git rev-parse -q --verify ORIG_HEAD ...)
     ORIG_HEAD 不会被 git commit --amend 更新
建议：改用 HEAD@{1}（reflog 前一条），它是被 amend 替换掉的真实 SHA
测试：
  1. 任意 AI 编辑 → commit
  2. 再 AI 编辑 → git commit --amend
  3. 检查 git note 应包含 prompts，stats 应有 ai_additions
```

## 给用户的修复建议（如果是环境）

要包含：

1. **明确的根因**（不要含糊"可能是某某问题"）
2. **具体操作步骤**（精确到命令、配置项、菜单路径）
3. **验证方法**（怎么确认修复了）
4. **如果环境问题反复出现，提示开发者考虑代码增强**

例：
```
症状：插件 sh hook 在你机器上找不到 sh.exe
根因：你从 .lnk 启动 Kiro，子进程没继承用户 PATH
解决：
  - 临时：从开始菜单启动 Kiro
  - 长期：在 .lnk 属性中加 "起始位置" = 包含 git/bin 的目录
验证：DevTools Console 看到 "Detected sh.exe via git --exec-path"
```
